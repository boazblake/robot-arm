## Diagnostic implementation

- `src/tracking/model/pose-world-diagnostic.ts` defines immutable `Point3D`, explicit axis documentation, hip center `(23,24)`, pure X/Y/Z rotations, orthographic projection, distances, and snapshot series.
- `src/tracking/model/tracking-frame.ts` exposes optional `poseWorldLandmarks` without changing existing callers that do not provide it.
- `holistic-service.ts` reads web `poseWorldLandmarks`; normalization preserves it when present.
- The **Freeze pose-world diagnostic** control in `src/app/hud/pose-viewer.ts` captures one source frame. Once frozen, the renderer uses only the frozen 33-point pose-world source, hip-centered Y rotation, and orthographic X/Y projection. Face and hands are excluded.
- The **Log pose-world snapshots** action emits full-precision JSON for 0, 45, 90, 180, 270, and 360 degrees, including frame ID, axis/degrees, center, source, rotated, projected points, and max 0°/360° error.

MediaPipe Pose World convention used here: meters; +X right, +Y down, +Z away from camera (smaller z is closer). This is documented by the Tasks Vision Pose Landmarker API; it is not inferred from the canvas appearance.

## Mathematical test results

`src/tracking/model/pose-world-diagnostic.test.ts` verifies:

- 0° identity, 360° identity within floating-point tolerance.
- Y(+90) then Y(-90) identity.
- Y(180) twice identity.
- Known-point 90° test exposes `x' = z`.
- All required 3D bone lengths remain unchanged at 0/45/90/180/270/360°.
- Every snapshot references the same immutable frozen source.

## Runtime evidence and classification

A real 0/45/90/180/270/360 snapshot requires a live MediaPipe frame and is intentionally generated by the diagnostic control rather than fabricated in this repository. The console JSON is the requested runtime evidence. In particular, at 90° orthographic projection, horizontal position is the source Z value (`x' = z`), so the view directly tests MediaPipe depth rather than hiding it with perspective.

The synthetic and rigid-body tests establish the transformation stage independently. If the runtime series keeps all 3D distances constant and 0°/360° agree, but 90° is anatomically implausible, the evidence classifies the issue as **Case C: source Z geometry / MediaPipe depth estimation**, not rotation mathematics. If 0°/360° diverge, inspect source freezing or state mutation. Face and hands remain intentionally unresolved.

No Z multiplier, correction constant, perspective, face integration, or hand integration was added.
